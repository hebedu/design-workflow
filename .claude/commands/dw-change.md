# 变更轮（/dw-change）

你是项目变更管理的协调者。当用户在已有产出的基础上提出**新需求 / 修改 / 修复 / 方向调整**时，本命令负责：**分诊变更类型 → 分析影响范围 → 推荐回路路径 → 协调局部执行**。

## 什么时候触发

用户说类似的话：
- "再加个 X 功能" / "增加一个 X" → A 类（增量新功能）
- "把 X 改成 Y" / "X 不好用，改一下" → B 类（修改现有功能）
- "走查发现 X 用不明白" / "上线后用户反馈 X 不行" → C 类（上线后修复）
- "方向错了" / "推倒重来" / "不做 X 改做 Y" → D 类（方向调整）

也支持自然语言触发，不一定要打 `/dw-change`。

## 执行步骤

### Step 1 · 读取项目当前状态
- `workspace/.current-project`
- `workspace/<项目>/manifest.json`
- `workspace/<项目>/00-shared-brief.md`
- 列出已完成的角色和产出文件

### Step 2 · 变更分诊（4 类）

询问用户（如果不明显）：

```
你的变更是哪一类？

A. 增量新功能 — 加个新东西，不影响现有功能
   例："再加个数据导出"

B. 修改现有功能 — 改现有功能的体验或逻辑
   例："任务列表加个筛选" / "登录方式改成手机号"

C. 上线后修复 — 走查或用户反馈发现的问题
   例："06 走查发现 A 功能用户用不明白"

D. 方向调整 — 共识书层面的改动
   例："不做企业版了，转个人版" / "目标用户从财务改成法务"
```

也可以根据用户原话自动判断，把判断结果告诉用户确认。

### Step 3 · 影响范围分析

根据变更类型，自动列出影响清单：

#### A 类（增量新功能）的典型影响
- ✅ **共识书**：检查"不做清单"——新功能是否在不做清单里？
  - 如果在 → 必须先 `/dw-align` 修订共识书
  - 如果不在 → 不影响共识书
- ✅ **01 研究**：可选，如果是大功能（用户画像/场景需要新增）
- ✅ **02 PRD**：必跑——加新功能描述、用户故事、优先级、PART 0.5 运营反证
- ✅ **03 交互**：必跑——加新功能流程、状态机扩展、组件清单更新
- ✅ **04 原型视觉**：必跑——加新页面/组件，如果改动大可能要重审风格
- ✅ **05 评审**：必跑——只评审新增部分 + 与现有功能的一致性
- ⚠️ **06 走查**：上线前再跑

#### B 类（修改现有功能）的典型影响
- ✅ **共识书**：通常不影响（除非改的是核心定位）
- ❌ **01 研究**：通常不需要
- ✅ **02 PRD**：微调——更新对应功能的描述、用户故事
- ✅ **03 交互**：微调——更新对应流程、可能新增分支
- ✅ **04 原型视觉**：微调——更新对应页面
- ✅ **05 评审**：必跑——重点评审修改前后的一致性
- ⚠️ **影响连带分析**：自动检查这个功能被哪些其他功能依赖，连带可能影响

#### C 类（上线后修复）的典型影响
- ❌ **共识书**：不影响
- ❌ **01 研究**：不影响（除非是用户研究层面的发现）
- ⚠️ **02 PRD**：可能影响（如果修复涉及功能边界变化）
- ✅ **03 交互**：必跑——重新设计有问题的流程
- ✅ **04 原型视觉**：必跑——更新对应页面
- ✅ **05 评审**：必跑
- ✅ **06 走查**：再跑一次——确认问题已修复

#### D 类（方向调整）的典型影响
- ✅ **共识书**：必升 v2，旧共识书归档为 `00-shared-brief-v1.md`
- ✅ **01 研究**：必跑——可能整篇重做或部分重做
- ✅ **02-05 全部**：必跑——所有产出可能需要重审
- ⚠️ **可复用部分识别**：自动列出"哪些产出可能仍然有效"（如某些用户画像、某些通用组件）

### Step 4 · 输出变更清单

把分析结果输出给用户确认：

```markdown
## 变更分析

### 变更类型
[A/B/C/D] · [一句话描述变更]

### 共识书影响
- [✅ 不影响 / ⚠️ 需要修订 v1.1 / 🔄 需要升级 v2]
- [如需修订/升级，列出具体改哪里]

### 受影响的角色
| 角色 | 影响程度 | 需要做什么 |
|------|---------|----------|
| 02 PRD | 中 | 加 F8 新功能描述 + 用户故事 |
| 03 交互 | 中 | 加 F8 主流程 + 加状态机过渡 |
| 04 原型 | 小 | 加 1 个新页面 |
| 05 评审 | 必跑 | 评审新增部分 |

### 推荐回路路径
[共识书更新（如需）→] 02 → 03 → 04 → 05

### 受影响的现有功能（连带）
- F3 任务列表：因为新增 F8 导出，列表需要加"导出"按钮
- F5 详情页：因为新增 F8 导出，详情页需要加"导出本条"操作

### 跳过的角色
- 01：本次变更不影响用户画像/场景
- 06：上线前再跑

请确认这个分析对吗？我准备开始执行。
```

### Step 5 · 用户确认后执行

用户确认后，按推荐路径**逐个角色执行**：

1. 如需修订共识书 → 先调用 `/dw-align` 修订模式
2. 然后按顺序调用受影响的角色（如 `/dw-pm` → `/dw-ux` → `/dw-style` → `/dw-review`）
3. **每个角色启动时，必须告诉它"这是变更轮"**：
   - 在角色启动模板里加一段"## 变更上下文"
   - 包含：变更类型 / 这次只改什么 / 不要重写未变的部分

### Step 6 · 每个角色产出加 §0 变更日志段

变更轮中的所有产出文件（02-prd.md / 03-interaction.md 等），必须在 TL;DR 之前加一段 §0 变更日志：

```markdown
## §0 变更日志（v1 → v2）

### 本次变更
- **类型**：[A/B/C/D]
- **触发**：[用户原话或一句话描述]
- **共识书版本**：v1（未变） / v1.1 / v2

### 改动的章节
- §3.1 功能表：新增 F8 数据导出
- §3.5 业务角色矩阵：F8 加入权限分配

### 未改动的章节
- §1-2 不变
- §4-6 不变

### 与历史版本的关系
- v1 仍然有效作为基线
- v2 = v1 + F8（增量）

---
```

文件头的 `version` 字段相应升到 v2。

### Step 7 · 更新 manifest.json

变更轮完成后，更新 manifest：
- 受影响的角色 `outputs.<角色>.version` 升级（v1 → v2）
- 根级别加一个新字段 `iterations`，记录每次变更轮：

```json
"iterations": [
  {
    "id": 1,
    "date": "2026-05-25",
    "type": "A",
    "trigger": "用户要求加数据导出功能",
    "shared_brief_change": "v1 → v1.1（不做清单移除导出）",
    "roles_updated": ["02-prd", "03-interaction", "04-prototype-hifi", "05-review"],
    "roles_skipped": ["01-research", "06"],
    "by": "claude-code"
  }
]
```

## 重要约束

- ❌ **不要默认从头跑**——变更轮的核心价值是"只跑必要的"，不要让用户重做已稳定的部分
- ❌ **不要跨过共识书直接改下游**——如果变更涉及共识书的"不做清单"或"目标用户"，必须先 `/dw-align`
- ❌ **不要覆盖 v1 不留痕迹**——变更日志段必须显式写明改了什么，git 历史不算（人不会去翻）
- ✅ **影响连带必须显式列出**——改一个功能可能触发其他功能的微调，要主动识别
- ✅ **D 类（方向调整）必须用户拍板**——不能 AI 自己决定要不要升 v2
- ✅ **可以跳过的角色就跳过**——别为了"流程完整"硬跑，浪费用户时间

## 共识书版本管理规则

| 变更类型 | 共识书动作 |
|---------|----------|
| A 增量（不在不做清单里）| 不变 |
| A 增量（在不做清单里）| v1 → v1.1，从不做清单移除 |
| B 修改（不影响定位/用户）| 不变 |
| B 修改（涉及核心体验）| v1 → v1.2，更新对应字段 |
| C 修复 | 不变 |
| D 方向调整 | v1 → v2，旧版归档为 `00-shared-brief-v1.md` |

## 用户附带的输入

$ARGUMENTS

- 留空 → 询问变更类型 + 描述
- 含"加 X / 增加 X" → 推断为 A 类
- 含"改 X / 修改 X" → 推断为 B 类
- 含"修复 X / 走查发现 X" → 推断为 C 类
- 含"方向错了 / 推倒重来" → 推断为 D 类
