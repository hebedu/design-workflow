# 设计协作流程总说明（导演手册）

本目录是一个「AI 剧组」：**6 个主角色 + 1 个可选角色**按顺序接力，把一个模糊需求推进到可落地的视觉方案。
所有角色脚本与 AI 平台无关，Claude / GPT / Gemini 均可用。

---

## 一、角色清单与交付物

| 顺序 | 角色 | 脚本文件 | 核心产出 |
|------|------|---------|---------|
| 1 | 研究助理 | roles/01-researcher.md | 需求成立性 + 拆解 + 竞品 + 用户痛点 + **模拟用户数据案例**（§2.4）|
| 2 | 产品助理 | roles/02-pm.md | PRD + 功能清单 + 优先级 + **PART 0.5 运营反证 & 增长钩子** |
| 3 | 交互助理 | roles/03-interaction.md | 主流程 + 状态 + 异常路径 + 交互规则 + 交互文案 + **验收标准列 + 业务约束表** |
| 4 | 原型视觉助理 | roles/04-prototype-visual.md | **阶段 1**：风格分析 MD + 3 个静态风格预览 HTML<br>**阶段 2**：设计 Token MD + 完整交互单文件 HTML（首屏承接 02 增长钩子）<br>**阶段 3**：规范前端工程包（frontend/ 子目录，含 package.json / 组件 / 路由）<br>★ 阶段 3 必须先经过 05 评审 |
| 5 | 评审员 | roles/05-reviewer.md | 多视角评审 + 问题清单 + 回炉任务单 + **是否启用 07 软提示** |
| 6 | 上线走查员 | roles/06-uat-walker.md | **阶段 1**：走查清单（让你拿去线上跑）<br>**阶段 2**：走查报告 + 给开发的回炉清单 |
| 7 ★可选 | 上线运营助手 | roles/07-launch-ops.md | 价值提炼 + 渠道 + 文案 + 节奏 + 转化路径 + 数据观察目标（不写埋点字段）|

**核心说明**：
- **角色 1-5 是设计流程**（从需求到高保真，闭环在上线前）
- **角色 6 是线上质量循环**（产品已上线后用，不属于设计链路）
- **角色 7 是可选支线**（需要对外传播 / 用户教育 / 增长 / 案例时启用，由用户显式 `/dw-launch` 触发，05 评审会给软提示）

**核心特性**：
- **三阶段设计**：04 分 3 阶段——阶段 1 风格探索 + 阶段 2 高保真原型（必经，两次对话）+ 阶段 3 前端工程包（可选，需 05 评审通过后由用户显式触发 `/dw-package`）
- **骨架先行**：每个角色都支持骨架模式（5 分钟版），先全链路跑通再精修
- **接收体检**：02/03/04 拿到上游产出后先做 30 秒体检，发现问题立刻打回

> 备注：早期版本归档在 `../draft/`（原 04 原型助理 + 05 UI 设计师已合并为新 04 原型视觉助理），可对照参考。

## 二、使用步骤（每次新项目）

### Step 0：建工作区
```
workspace/
└── YYYY-MM-DD-项目名/
```

### Step 1：启动研究助理
1. 打开任一 AI（Claude / GPT / Gemini），**开新对话**
2. 复制 `roles/01-researcher.md` 的 **PART 1** 全文，粘贴给 AI
3. 复制 **PART 2** 启动模板，填好项目信息后粘贴
4. AI 按格式输出研究报告
5. 保存到 `workspace/YYYY-MM-DD-项目名/01-research.md`

### Step 2 ~ 5：依次调用后续角色
- **每次都开新对话**（避免上一角色人格残留）
- 粘贴下一角色的 PART 1
- 粘贴上一角色产出文件的完整内容作为输入
- 保存到对应的 `02-prd.md`、`03-interaction.md`、`04-style-options.md` + `04-prototype-hifi.md`（04 阶段 1+2 是两次对话两份文件；阶段 3 工程包可选）、`05-review.md`

> ⚠️ 注意：04 原型视觉助理是**三阶段**：
> - 阶段 1（必经）：风格探索 → `04-style-options.md` + 3 个静态 HTML
> - 阶段 2（必经）：高保真单文件 HTML → `04-prototype-hifi.md` + `04-prototype.html`
> - 🚧 **05 评审在阶段 2 和阶段 3 之间**
> - 阶段 3（可选）：前端工程包 → `frontend/`，仅当 05 评审通过 + 用户需要落地代码时才走（`/dw-package`）
>
> 阶段 1+2 是两次对话（必经）。阶段 3 是独立的第三次对话（可选 gate）。骨架轮不包含阶段 3。
> 1. 第 1 次（场景 A1）：输出 `04-style-options.md`（3 个风格方向）
> 2. 你选定 1 个风格
> 3. 第 2 次（场景 A2）：输出 `04-prototype-hifi.md`（高保真）

### Step 6：回炉迭代
评审员会输出「回炉任务单」，按角色分组，每组自带可复制的启动语。

1. 看评审报告末尾的「回炉优先级」表，确认哪些角色需要改
2. 按优先级顺序，把对应的「📤 给 xxx 的回炉任务」复制粘贴给那个角色
3. 角色输出 v2 版本后，保存覆盖原文件（或另存 `-v2`）
4. 如果某角色的修改影响下游（评审报告会标注"是否阻塞下游"），下游角色也要跟着更新
5. 全部回炉完成后，可再跑一轮评审员确认

## 三、跨 AI 使用建议

| AI | 擅长的角色 | 原因 |
|----|----------|-----|
| Claude | 产品助理、原型视觉助理、评审员 | 长文本、结构化输出稳、能写规范代码 |
| ChatGPT | 研究助理 | 联网搜竞品方便 |
| Gemini | 原型视觉助理 | 多模态，能看你的参考图（特别适合阶段 1 风格探索） |

## 三 .5、线上质量循环（角色 6 上线走查员）

设计流程（01-05）的终点是**高保真原型 + 评审通过**，但产品上线后还需要一个独立循环：**对真实运行的产品做走查**。

### 为什么独立成一环

| | 设计阶段评审（05） | 上线走查（06） |
|--|------------------|---------------|
| 对象 | Markdown / HTML 静态稿 | 运行中的真实产品 |
| 输入 | 文档 | URL / 截图 / 操作描述 |
| 关注 | 设计偏离 | 实现偏离 + 真实数据边界 + 性能 |
| 回炉给 | 设计角色（02/03/04） | 开发 / PM 决策 |

### AI 在走查中的角色

⚠️ **AI 不能自己跑测试**（看不到你的产品后台、不能模拟点击）

走查模式是 **「AI 教练 + 用户跑测试」**：

```
Step 1: AI 出走查清单（基于 PRD/交互规格）
   ↓
Step 2: 用户人工去线上跑（标 ✅/⚠️/❌/❓ + 截图描述）
   ↓
Step 3: 用户把标记结果交回给 AI
   ↓
Step 4: AI 整理报告，输出📤 给开发的回炉清单 + 📤 给 PM 决策的项
```

### 走查节奏

| 场景 | 用什么 | 频率 |
|------|--------|------|
| 上线前 | 完整走查（场景 A1 → A2） | 大版本前 1-2 次 |
| 灰度期 | 冒烟走查（场景 C，只 P0） | 每次部署后 |
| 修复后 | 回归走查（场景 B） | 修 bug 后验证 |
| 无文档 | 轻量走查（场景 D，基于 URL） | 应急 |

## 四、四条铁律

1. **角色不越界**：每个角色只做自己那一环，超纲就转交。
2. **产出走文件**：所有交接通过 Markdown 文件，不依赖 AI 的对话记忆。
3. **契约优先**：所有输出遵守 `handoff-contract.md` 的统一格式。
4. **人工在环**：你是总导演，AI 不自动触发下一步，由你决定何时推进。

## 五、灵活调用（重要：不必跑全链路）

这套流程**不是必须从头跑到尾**。每个角色都支持「独立调用」或「插入中段」，每个角色的 PART 2 都列了多种场景。

### 三种使用模式

#### 模式 1：全链路（默认，标准模式）
01 → 02 → 03 → 04（两次：阶段 1 + 阶段 2）→ 05 → 06，按顺序接力。适合从模糊需求开始的新项目。

#### 模式 2：单点调用（只用某一个角色）
打开你需要的那个角色，按它的 **PART 2 · 场景 B** 启动模板提供「最小输入」。AI 会基于你给的有限信息工作，缺失的部分在「假设与遗留」里标出。

**典型场景速查表**：
| 你已有 | 你想要 | 直接调用 | 用哪个场景 |
|--------|-------|---------|-----------|
| 一个需求点子 | 拆需求 + 找竞品 | 01 研究助理 | 默认 |
| 写好的需求描述 | 一份 PRD | 02 产品助理 | 场景 B |
| PRD | 交互流程 + 状态 | 03 交互助理 | 场景 A |
| 大致功能列表 | 交互规格 | 03 交互助理 | 场景 B |
| PRD 或交互规格 | 3 个视觉风格方向 | 04 原型视觉助理 | 场景 A1（阶段 1） |
| 阶段 1 已选定风格 | 完整高保真 + Token + 提示词 | 04 原型视觉助理 | 场景 A2（阶段 2） |
| 大致需求 | 直接出风格 + 高保真 | 04 原型视觉助理 | 场景 B |
| **已有 HTML 页面** | **美化 + 出 Token + AI 提示词** | **04 原型视觉助理** | **场景 C** ★ |
| 完整方案 | 全盘评审 | 05 评审员 | 场景 A |
| 部分产出 / 半成品 | 局部评审 | 05 评审员 | 场景 B |
| **已上线产品** | **生成走查清单** | **06 上线走查员** | **场景 A1** ★ |
| 跑完清单要出报告 | 整理走查报告 + 回炉清单 | 06 上线走查员 | 场景 A2 |
| 修了问题想复测 | 回归走查清单 | 06 上线走查员 | 场景 B |
| 每次部署后快速验证 | 冒烟走查（只 P0） | 06 上线走查员 | 场景 C |
| 没文档但已上线 | 基于 URL 的轻量走查 | 06 上线走查员 | 场景 D |
| **设计完成需推广发布** | **上线运营方案（价值/渠道/文案/节奏）** | **07 上线运营助手**（可选）| **场景 A** ★ |
| 单一文案急用（更新日志 / 标题 / 短视频口播）| 局部文案 | 07 上线运营助手 | 场景 C |

#### 模式 4：增强模式（标准 + 07 上线运营）
满足以下任一条时，05 评审完成后用户显式触发 `/dw-launch` 启动 07：
- 新功能上线需要对用户说明 / 站内 Banner / 更新日志 / 弹窗
- 需要做小红书 / 公众号 / 视频号 / 官网 / 社群发布
- 需要做用户教育 / 增长拉新 / 案例包装 / 汇报材料

不满足上述条件的（内部后台 / bug 修复 / 字段调整 / 纯样式优化）默认跳过 07。

#### 模式 3：插入中段
中间跳过某些环节直接从下游开始。比如已有 PRD + 选定风格，跳过交互规格，直接进 04 阶段 2。
每个角色都会基于你提供的输入工作，并在「假设与遗留」里明确指出"缺少 XX 环节"。

### 使用准则
- **跳过的环节，AI 不会替你脑补** —— 它只基于你给的输入工作
- **缺失会影响产出时**，AI 会在「假设与遗留」里显式标出
- **可以反向补齐** —— 后期想做用户研究 / 补 PRD，回头调用对应角色即可
- **跳得越多，假设越多** —— 评审员的健康度评分会更低，要心里有数

## 六、反瀑布：骨架先行 + 接收体检 ★

瀑布流最大的痛点是「做完最后一棒才发现第一棒就错了」。这套流程通过两个机制把问题前置：

### 机制 1：骨架先行（场景 S）

**核心主张**：先全链路跑一遍最粗的"骨架版"，看到端到端的样子，再回头精修。

每个角色都支持「场景 S：骨架模式」：
- 只输出最小必要内容（5 分钟等价工作量）
- 文件头 `version: skeleton-v1`、`status: skeleton`
- 用 `[TBD - 精修时展开]` 占位那些故意不做的细节

**典型流程**：
1. 跑完整骨架轮：01→02→03→04（骨架版，1 次对话不分阶段）→05（每棒 5 分钟，1 小时看到端到端）
2. 评审员拿到骨架产出后，给出"骨架阶段的发现"（偏方向性，不纠细节）
3. 导演决定：哪些环节值得精修？哪些压根不对要改方向？
4. 回头精修需要的角色（`version: v1`、`status: draft`），04 在精修阶段再走两次对话（阶段 1 + 阶段 2）
5. 再跑一次评审

**好处**：
- 发现"方向错了"的成本从 N 天降到 1 小时
- 所有角色能提前看到端到端，自己的产出更有全局感
- 避免精修了一份 PRD，到原型阶段才发现整个方向要重来

### 机制 2：接收体检（PART 0）

**核心主张**：每个角色拿到上游产出后，**不要立刻开工**。先做 30 秒接收体检，发现问题立刻打回，别做完才发现。

每个下游角色（02/03/04）的文件里都有 PART 0，列出该角色对上游的体检项。05 评审员本身就是质量卡点，不需要 PART 0。

**体检结论三选一**：
- ✅ **通过**：上游产出可用，开始工作
- ⚠️ **有风险继续**：列出风险，继续做但标注依赖
- 🛑 **打回**：列出必须先改的问题，停下不产出，回到上游角色

**好处**：
- 不会浪费时间做在烂输入上
- 上游的问题暴露在下游出错之前
- 每棒开始前都有个强制的质量卡点

### 机制组合：怎么用

**小项目（2-3 天）**：
- 只用骨架先行。全链路跑骨架 → 评审 → 精修。

**中型项目（1-2 周）**：
- 骨架先行 + 接收体检都用。骨架轮里接收体检会很快（输入都是草稿）；精修轮里接收体检保证每棒输入质量。

**大项目（月级）**：
- 骨架轮 + 精修 + 接收体检，且每个关键环节后可插入评审员做 gate review（局部评审，场景 B）。

## 八、常见坑

- **AI 越权写 PRD**：研究助理开始自己写功能清单 → 在 PART 1 里明确边界，并在对话里提醒一句「只做研究那一步」。
- **上下文串味**：同一对话里切换角色，AI 会带前一角色偏见 → 每个角色都新开对话。
- **产出格式漂移**：AI 不按契约输出 → 在启动模板末尾强调「严格遵守 handoff-contract.md」。
- **版本混乱**：迭代时覆盖旧文件 → 文件名带 `-v1`、`-v2`，或用 git 管理 workspace。
