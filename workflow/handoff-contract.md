# 交接契约（所有角色必须遵守）

任何角色的输出都必须包含三段：**文件头 + 正文 + 交接尾**。

---

## 一、文件头（YAML Frontmatter）

每份产出文件顶部必须有：

```yaml
---
role: [角色名]
project: [项目名]
date: [YYYY-MM-DD]
version: v1            # 每次迭代自增：v1 / v2 / v3
upstream: [上游文件路径或 "无"]
downstream: [下游角色名]
status: [draft / final]
---
```

---

## 二、正文

由每个角色的脚本规定（见各 role 文件的 PART 3），但必须包含：

- **TL;DR**：不超过 100 字的一句话总结
- **具体交付**：按角色定义的结构化内容

> **正文具体字段由各角色 PART 3 规定**，本契约不重复列出（避免与角色脚本失同步）。如下游需要的关键内容（如 02 的「🚀 增长钩子」段、03 的「验收标准」列、01 的「模拟用户数据案例」），由各角色在自己的 PART 3 输出格式中显式定义并强制输出。

---

## 三、交接尾

每份产出末尾必须有：

```markdown
---

## 🤝 交接

### ✅ 已完成
- [列出本次完成的关键项]

### ⚠️ 假设与遗留
- [基于的假设、未解决的问题、需要人工确认的点]

### 📤 给下游的钩子
- [下游角色需要重点关注的部分，例如"用户痛点 #3 必须在 PRD 中有对应功能"]

### 🔗 启动下游
复制以下内容粘贴给下一个 AI：

> 我是下游角色 **[下游角色名]**。
> 上游产出文件：`workspace/<项目名>/<上游文件名>`
>
> ## 上游 TL;DR
> [粘贴本文件的 TL;DR，通常 100 字内]
>
> ## 给我的钩子（重点关注）
> [粘贴本文件「📤 给下游的钩子」那一节]
>
> ## 后续指令
> 请读取上游文件完整内容，按你的脚本处理。
> 如果你在网页版 AI 中无法读文件，请告诉我，我会粘贴完整内容。
```

---

## 四、为什么要这样设计

| 段落 | 作用 |
|------|-----|
| 文件头 | 让下游一眼看到输入输出关系、版本号 |
| TL;DR | 你扫一眼就知道这份产出的主旨，不用读全文 |
| 假设与遗留 | 防止 AI 瞎编，让不确定性显式化 |
| 钩子 | 防止关键信息在接力中丢失 |
| 引用模式启动语 | CC / Codex / Cursor 直接读文件，避免 token 爆炸；网页版 AI 用户看到提示后主动粘贴 |

## 六、增长钩子段（02 → 04 / 07 专用）

02 产品助理输出 PRD 时，必须在交接尾的「📤 给下游的钩子」之后，附加一段**增长钩子**，供 04 原型视觉助理和 07 Launch Ops 承接。

格式如下：

```markdown
### 🚀 增长钩子（来自 02 PART 0.5 运营反证）

- **价值表达方向**：<一句话用户能听懂的核心价值>
- **首次触发点**：<用户什么时候 / 在什么场景下会想用>
- **使用阻力**：<用户为什么可能不用 / 不敢用 / 用不出效果>
- **推广钩子**：<功能上线后哪些点值得对外说，3 条以内>
- **观察目标**：<怎么算成功，写观察目标，不写埋点字段>
```

### 谁承接

- **04 原型视觉助理（阶段 2）**：主页面 / 首屏必须体现「价值表达方向」（标题、Banner 或入口副文案三选一），CTA 文案需呼应「首次触发点」
- **07 Launch Ops（可选）**：把「价值表达方向 / 推广钩子 / 观察目标」作为输入，扩展为完整上线运营方案

### 不要做

- ❌ 不写埋点 event 名 / 字段（那是 04 阶段 3 或独立埋点步骤的事）
- ❌ 不写完整营销渠道方案（那是 07 的事）
- ❌ 不写 UI 文案细节（那是 04 阶段 2 的事）
- ❌ 不夸大功能效果，所有判断都要可被反驳

## 七、变更日志段（变更轮专用，v4.9.8 起）

如果产出是**变更轮的产物**（即不是 v1，而是基于已有产出做的增量 / 修改 / 修复 / 重启），必须在 TL;DR 之前加一段 §0 变更日志。

### 何时需要

| 触发场景 | 是否需要 §0 变更日志 |
|---------|-------------------|
| 第一次跑这个角色（v1）| ❌ 不需要 |
| 通过 `/dw-change` 触发的变更轮 | ✅ 必需 |
| 评审打回后的回炉（v1 → v2 但是修复，不是新需求）| ⚠️ 推荐（写"评审回炉"类型）|
| 用户直接说"重做这部分"（不走变更轮）| ⚠️ 推荐 |

### 标准格式

```markdown
## §0 变更日志（v(N-1) → vN）

### 本次变更
- **类型**：[A 增量 / B 修改 / C 修复 / D 重启 / R 评审回炉]
- **触发**：[用户原话 / 评审编号 / 走查发现]
- **共识书版本**：[v1 未变 / v1.1 / v2]

### 改动的章节
- §X.Y：[一句话改了什么]
- §X.Y：[一句话改了什么]

### 未改动的章节
- §A-B 保持 v(N-1) 内容
- §C 保持 v(N-1) 内容

### 与历史版本的关系
- v(N-1) 仍然作为基线参考
- vN = v(N-1) + [增量内容] / 替换 [章节] / 修复 [问题]

### 给评审的提示
- 重点评审：§X.Y（变更点）+ 变更对 §A.B 的连带影响
- 可以跳过：§C-D（未变化）

---
```

### 文件头版本号规则

- 第一次跑：`version: v1`
- 变更轮后：`version: v2` / `v3` / ...
- 骨架版：`version: skeleton-v1`
- 骨架版升级到完整版：`version: v1`（重置）

### 不要做

- ❌ 不要在 v1 文件里加变更日志段（v1 没有"前一版"可比）
- ❌ 不要把变更日志写得像 commit message（要让人看完就知道下游受什么影响）
- ❌ 不要省略"未改动的章节"——下游需要知道哪里可以信任旧版本
- ✅ 变更日志段是给下游的"导览图"，让评审/下游不用通读全文就能定位变化
